# 三色六角碁 (Three Color Hex Go)

**黒・白・赤の3色で遊ぶ、六角格子の変則囲碁**。得点は陣地ではなく**終局時に盤上に残った自分の石数**だけです。

> v1.5.0 は独自ルールの試作版です。CPUは3手先までの候補を限定探索しますが、プロ棋士レベルの囲碁AIではありません。



## 学習曲線：残った石数・取った石数・固定CPUへの強さ（PR #23）

これまでの探索なしAIは学習中の局ごとの`scores`・石数割合を計算していたものの、**学習ログへ保存せず、480局終了時点の1モデルだけを対CPU評価**していました。そのため、「学習率を下げたらもっと長い学習が必要だったのか」「石数が途中で増加したのか」は従来のログでは判断できません。

この実験は、各反復に黒白赤の**終局残存石数・獲得捕獲石数・奪われた石数**、総残石数、ゼロ石終局率、総手数、価値予測MSE、方策KL/entropyを出力します。`--checkpoint-every N`により学習途中の重みを保存し、**同じ評価シードで基本型2人および難しい＋バランスとの対戦**を繰り返します。

- 追加学習：学習率0.0001、**960局（120反復×8局）**、半径2/3/4（大盤面の実力は未検証）。160/320/480/640/800/960局時点でそれぞれ評価する。
- 自己対戦の全3人の平均石数割合は恒等的に33.3%となるため、**その値は上達の指標にしない**。相手固定の勝率・石数割合と、盤面サイズ別の生残石数・捕獲数の時系列を重視する。
- [960局の実験ワークフロー](https://github.com/nao70161994/three-color-go/actions/runs/41221126368)
- 本番CPU・公開サイト・重みは変更しない。実験専用PRのまま評価する。

## 学習率比較＋複数CPU評価（PR #22）

探索なし・3人共有Actor-Criticについて、学習率4条件（0.001/0.0003/0.0001/0.00003）を各480局の同条件で比較しました。評価は**難しい・バランス・戦術型・防御型・基本型**と対戦し、黒白赤の全6席順を入れ替え、各学習率96局を計測しました。

- 各反復の方策KL（更新前後）、正規化エントロピー、価値MSEを記録。旧「難しい」＋「バランス」には全条件で勝てず、**公開CPUの重みは一切変更していません**。

## 実験：探索なし・3人同時自己対戦・最終石数割合（PR #21）

前段のPV2+MCTSとは**別方式**です。黒・白・赤の3人が共通のPV2ニューラルネットワークを使って自己対戦し、3人全員の着手履歴をまとめて**1つの共有モデル**を更新します。

- **報酬100%：**各色 `終局時の残存石数 ÷ 3色の残存石数合計`。3人の報酬合計は1、石が0個なら等分。勝利ボーナス、捕獲ボーナス、教師の着手スコアは使いません。
- **探索なし：**1手につきニューラルネットの推論を1回だけ行い、合法手の確率分布から自己対戦中はサンプリング、評価対戦中は最大確率を選択。**MCTS、rollout、3手先読み、戦術スコアフィルタなし**。合法手の列挙にはゲームルールの`play`を使います。
- **同時学習：**黒・白・赤はすべて同じ凍結重みで1局をプレイします。1反復分の3人全員の局面を収集後、1つのネットワークの方策・価値を同時に更新（on-policy Actor-Critic/REINFORCE）。価値出力は各色の最終石数割合を予測し、行動方策の更新には`石数割合 − 推定価値`の利得とentropy正則化を使います。
- **探索型PV1/PV2と旧CPUをそのまま保持**。実験モデルを公開CPUへ自動採用せず、測定基準を満たすまで候補重みをGitHub Actionsで別管理します。

```bash
python -m pip install torch numpy
npm run train:direct -- --iterations 60 --games 8 --radii 2,3,4 --seed 20261101 --out reports/direct-candidate.json
npm run parity:pv2 -- reports/direct-candidate.json
npm run benchmark:direct -- --model reports/direct-candidate.json --games 24 --radius 3 --seed 20261121
npm run benchmark:direct -- --model reports/direct-candidate.json --games 24 --radius 4 --seed 20261122
```

**初期結果：**108局（18反復×6局、20261101）で学習した候補は、半径3で`0/24`局・平均石数差`−21.625`、半径4で`0/24`局・平均差`−31.750`と、双方とも旧「難しい」を上回れませんでした。モデル推論のJS/PyTorch整合性チェックは成功。これは仕組みの動作確認であって棋力向上の証明ではありません。

- [108局の学習・対戦・候補重み](https://github.com/nao70161994/three-color-go/actions/runs/41215732952)

**追加検証（480局＝60反復×8局、合計38,874手番の学習サンプル）**：前回と同じ独立評価シード、半径3/4で24局ずつ比較しました。

| 学習局数 | 半径3：石数勝ち（対「難しい」） | 半径3：PV−難しい石数差 | 半径3：PV最終石数割合 | 半径4：石数勝ち | 半径4：石数差 | 半径4：PV石数割合 |
|---|---:|---:|---:|---:|---:|---:|
| 108局 | 0/24 | −21.625 | 6.60% | 0/24 | −31.750 | 3.93% |
| 480局 | 0/24 | −20.125 | 2.76% | 0/24 | −32.750 | 3.74% |

結果：108→480局でも棋力の改善は確認できません。半径3の平均差は小幅改善しましたが、石数割合は悪化。両盤面の石数勝ちは0局です。学習損失は下降しても対戦力は改善しないため、**追加学習だけでなく、方策の探索性、価値推定、相手の多様性、ネットワークの表現力を再検証する必要があります**。この少数シードの対戦結果は棋力の統計的証明ではありません。

## PV2報酬関数の比較実験（PR #20）

前段のPV2実験で、ニューラルネットワークの価値目標は「勝敗75%＋最終石数25%」、**MCTS探索の実際の終局値は勝敗100%**と不整合でした。報酬を `src/pv-reward.js` に統合し、探索の終局評価・自己対戦の学習目標をモデルの `rewardProfile` によって一致させました。

| `--reward-profile` | 3人の終局報酬（合計1） |
|---|---|
| `winner` | 勝敗100%（同率首位は均等に分割） |
| `blend` | 勝敗75%＋最終盤面の石数割合25% |
| `margin` | 勝敗75%＋「各人の石数差を最大差で正規化した値」のsoftmax25% |

**2026-11-01の同条件比較**：各方式とも初期乱数20261031、12反復×6局＝72局、学習中のMCTS探索12回。半径2・3・4を循環して学習。評価は半径3/4それぞれ24局、評価時探索16回、同じ席順6通りと未使用シード（20261121・20261122）、対戦相手は変更していない「難しい」と「balanced」です。

| 報酬 | 半径3: PVが難しいより石数で上 | 半径3: PV−難しい平均石数 | 半径4: PVが上 | 半径4: 平均石数 |
|---|---:|---:|---:|---:|
| `winner` | **7/24**（同石数1） | **−10.083** | 0/24 | −31.250 |
| `blend` | 1/24 | −18.417 | 0/24 | **−28.875** |
| `margin` | 2/24 | −17.792 | 0/24 | −31.792 |

この範囲では、半径3で `winner` が相対的に良い結果でしたが、半径4は**全方式が石数で「難しい」に24戦全敗**。全モデルとも昇格条件を満たさず、公開版CPUや本番重みは変更していません。同一計算条件でも各報酬が誘導する自己対戦棋譜は異なります。各盤面24局という小さなサンプルから、勝敗報酬の普遍的な優位性は断定できません。学習量・探索数・未使用シードを増やして再検証する必要があります。

- [GitHub Actions実験結果・3候補モデル・対戦JSON](https://github.com/nao70161994/three-color-go/actions/runs/41214481740)
- 実行例：`python scripts/train-pv2-selfplay.py --reward-profile winner --iterations 12 --games 6 --simulations 12 --radii 2,3,4 --seed 20261031 --out reports/pv2-winner.json`
- 比較例：`node scripts/benchmark-pv.mjs --model reports/pv2-winner.json --games 24 --radius 3 --simulations 16 --seed 20261121`

既存のモデルJSONに `rewardProfile` がない場合は、旧PV1を `winner`、旧PV2を `blend` として解釈します（後方互換）。

## PV2研究実験：石群を考慮する多段ネットワーク（PR #19）

**未公開の実験コードです。** 前段のPV1で局所1段の情報伝播と終局勝敗のみの学習では「難しい」に負けたため、実際の3人対局の石群状態を入力へ追加する方式を検証しています。

- `src/pv2-ai.js` は盤面の全マスの相対石色、空点、進行度に加え、**連結石群の呼吸点数・石数**を全盤面にエンコード。3段の共有メッセージパッシングで16次元特徴を伝播し、各点＋パスの方策と3人の勝利見込みを予測します。
- `src/pv-ai.js` のMaxN/PUCT探索はPV1とPV2双方に対応。PV2では自己対戦の根で再現可能なノイズを加えて探索を多様化します。
- `scripts/train-pv2-selfplay.py` は**人間の棋譜や手作り教師のスコアを使用しません**。本物のJSルールで対戦したMCTS訪問分布と終局勝利配分・最終石数割合から方策と価値を学びます。石群の呼吸点特徴は正解の教師スコアではなく盤面の観測量です。
- 終局時の石数が得点となる独自ルールに合わせ、探索のCPUは安全な着手が残る間は早期パスを候補に入れません（人間がパスするルールは変更なし）。
- JavaScript/PyTorchの**重み・推論一致検査** `scripts/check-pv2-parity.py` を追加。ゲーム配信に用いるモデルは変更せず、学習したJSONをアーティファクトとして保存します。

## v1.7 実験中：盤面全体のPolicy-Value Network＋3人用MCTS

従来の「12特徴量で1手を採点するニューラルCPU」とは別に、**盤面全体から推論して読みを入れる**実験用AIを実装しました。**未学習モデルを製品として出さない**ため、ゲーム画面の難易度メニューにはまだ追加していません。

### 設計
- 入力は盤面半径2〜12を収める **8面×25×25マス**。黒・白・赤の石配置（3面）、有効マス（1面）、手番（3面）、対局の進行度（1面）。各手について個別に12種類の特徴量を算出する方式ではありません。
- 軽量な **畳み込みニューラルネットワーク（CNN）** が、盤面上625地点＋パスの着手スコアと、黒・白・赤それぞれの勝利見込みを同時に出力します。
- **3人対応のMaxN/PUCT MCTS**：探索途中ではその手番のプレイヤー本人の期待勝利配分を最大化します。2人対戦のように値の符号を反転する方式ではありません。同点の終局結果では勝利配分を等分します。
- 自己対戦は実際の JavaScript ルールエンジンで実施し、**MCTSの訪問回数分布を方策の学習目標、終局勝利配分を価値の学習目標**にします。教師スコアや人間の棋譜は不要です。石の合法性とスーパーコウは従来どおりゲーム本体で検査します。
- 探索時には既存CPUと同じ眼埋め・危険な自アタリのフィルターを使い、安全な着手候補がある場合はパスを選ばないようにします。これは**教師スコアや正解ラベルではなくCPUの候補手制約**です。人間プレイヤーの合法手や対局ルールを変更しません。
- 実験用学習器 `scripts/train-board-mcts.py` はランダム初期化から学習し、候補JSONに保存。既存の `src/neural-weights.js` は一切置き換えません。
- PythonのCNN推論とJavaScriptのCNN推論が一致することを `scripts/check-board-parity.py` で数値検証します。

## v1.7 実験中：盤面全体の Policy-Value Network + 3人用 MCTS

既存の12特徴量・1手評価型とは異なり、**盤上の全交点**を相対色（自分、次の相手、もう1人の相手、空点）および進行度として入力します。共有16次元埋め込みと六角格子の隣接点集約を使う小型ニューラルネットで、全交点＋パスの方策スコアと、3プレイヤーの予測勝利配分を同時に出力します。

- **3人対応MaxN型PUCT探索**：各節点ではその時点の手番プレイヤーにとっての勝利見込みを最大化し、伝播する価値は黒・白・赤の3成分のまま保持します。2人零和ゲームのような単純な符号反転はしません。
- **教師なし（自己対戦の報酬による学習）**：MCTS訪問数分布を方策目標、終局の勝利配分（同率首位は等分）を価値目標にしてPyTorch学習。人間の棋譜や手作りの戦術評価点は使用しません。合法手／危険手のフィルタなどのルール依存処理は残ります。
- **実験用モジュール**：`src/pv-ai.js`。学習モデルはJSONで出力され、**現在公開中の「ディープラーニング」CPUや「難しい」CPUには自動適用されません**。
- **現段階での制約**：共有層2段・16次元という小さなネットワークなので、盤面全域にまたがる複雑な戦術を十分表現できるとは限りません。推論とMCTSはモバイルの速度制限を考慮して段階的に最適化する必要があります。

```sh
# Python 3 / PyTorch / NumPy / Node 22
python3 -m pip install numpy torch
npm run train:pv -- --iterations 8 --games 4 --simulations 12 --radii 2,3,4 --out reports/pv-candidate.json
npm run benchmark:pv -- --model reports/pv-candidate.json --games 60 --radius 3 --simulations 16 --seed 20261101
```

## v1.6 開発中：教師スコアを使わない自己対戦強化学習

従来の「ディープラーニング（実験版）」は手作り戦術スコアを模倣した**教師あり蒸留モデル**で、現時点のゲームにはこの旧モデルを搭載したままです。新しい方式では教師スコアや人間の棋譜を使わず、3人が同じモデルで対戦して**終局時の勝敗と石数差だけ**を報酬にする REINFORCE（方策勾配）を導入しました。

学習開始時はランダム重みです。盤面ルール、12種類の手作り入力特徴量、眼・自アタリ回避などの安全フィルターは引き続き使います。そのため「完全な生盤面からの学習」ではありませんが、**正解の着手や教師評価点は与えていません**。探索に基づく AlphaZero 方式でもありません。

### 学習と比較の実行

Python 3（PyTorch・NumPy）と Node.js 22 以上を用意してください。

- `scripts/train-selfplay-rl.py` は反復ごとに最新モデルで自己対戦し、選んだ手の確率を結果に応じて更新します。模倣学習用の `scripts/train-neural-policy.py` は比較・再現用に残しています。

### CPU3人の対局を観戦

対戦モード「**CPU 3人の対局を観戦**」では、黒・白・赤の3人をAIが自動操作します。観戦者は石を打てませんが、**一時停止・再開・1手進める・速度（ゆっくり／ふつう／速い）**を操作できます。CPUの強さは3人に同じ設定を適用します。途中で棋譜再生するとAIの手番も止まり、再生を閉じれば元の観戦状態へ戻ります。

397・469マスなど半径8以上の盤面には「**拡大表示／全体表示**」切り替えがあります。拡大表示では盤をスクロールしながら操作できます（スマホでもページ全体の横スクロールは避けます）。

\`\`\`js
const go=window.threeColorGo;
go.reset({mode:'bots',radius:11,cpuLevel:'easy'});
go.pauseBots();
go.stepBot();               // AIが1手着手
go.getPresentation();       // spectatorPaused, spectatorSpeed, zoomBoard
go.setSpectatorSpeed(180);  // 速い (ms)
go.setBoardZoom(true);      // 盤面を拡大
go.resumeBots();
\`\`\`

AI・Codexなどの検証エージェントは従来の\`getState()\`、\`legalMoves()\`、\`exportRecord()\`、\`importRecord()\`を引き続き利用できます。巨大盤面で「むずかしい」を使う場合、思考時間を抑えるため候補手を事前選別します（全合法手の完全探索ではありません）。大きな盤面ほど長期戦になります。

## v0.7：最小盤面の見直しと強いCPU

- **小さい盤面を19→37マス**に変更。新規の盤面選択は小37／標準61／大91／特大127マスです。19マスで進行中の旧セーブ・棋譜はそのまま読み込めます（旧19マスの新規選択だけ無効化）。
- **「むずかしい」CPU**に3手分の候補探索（CPUの着手→相手1→相手2）を導入。各相手の有力な応手を評価し、2人で石を囲まれるリスクやグループの呼吸点も考えます。計算量を抑えるため盤面が大きいほど候補幅を絞っています。
- 「やさしい」「ふつう」は従来どおり。石数得点・自殺手・コウ・終局のルールは変更していません。
- 先読みは万能ではありません。強さは旧CPUとの**同じ条件での勝率・対局再現・処理時間**で継続評価します。

\`\`\`sh
npm test
npm run test:strength -- --games 60 --radius 3 --seed 20261031 --out reports/strong-v0.7.json
\`\`\`

この比較は新CPU1体と従来の\`balanced\` CPU2体の試合で、新CPUの担当色を順番に交代します。AI同士の結果であり、人間の勝率や棋力を保証するものではありません。

## v0.6: CPU対戦の研究とゲームバランスの可視化

**三色六角碁のルールは変更していません。** 同じ石数得点、六角盤、呼吸点の判定です。

- 「むずかしい」CPUに **2人の相手による次手の捕獲リスク**の確認を追加しました（\`balanced\` 戦略）。完全な深読みではなく局所的な危険度推定です。以前の \`guarded\` も検証用に残しています。
- AI同士で手番ごとの勝率を測定。黒の優位性を確かめる際は、同じAI3体を使い、引き分けの勝利点を均等配分します。
- **終盤が単調かどうかの代理指標**：盤上占有率、80%以上の盤面充填率、最終3分の1に捕獲がない着手の割合、首位交代回数、共同捕獲数を集計。
- **新旧AI比較**：\`balanced\` 1体と \`guarded\` 2体で、挑戦者を黒・白・赤に交代させながら対局させ、手番位置と強さの影響を分けて観察します。
- 再現可能な乱数シードと棋譜を保存し、問題が出た対局をブラウザの \`importRecord()\` と \`openReplay()\` で検証できます。
- レポートは **GitHub Actions → tests → balance → Artifacts** にJSONとして保存します。

\`\`\`sh
npm test
# 90局の新CPU同士：位置の偏り、終盤の傾向
npm run balance -- --games 90 --radius 3 --seed 20261031 --out reports/balance.json
# 新CPU vs 旧CPU2体：各色30回ずつ、合計90局
npm run balance:matchup -- --games 30 --radius 3 --seed 20261031 --out reports/matchup.json
\`\`\`

**解釈上の注意**：AIの勝率は人間の勝率ではありません。「80%以上埋まる」ことは単調さの可能性を示す指標ですが、プレイヤーが退屈する証拠ではありません。先手有利があっても、十分な人間の対局データが揃うまではコミや得点ルールを変えません。

## v0.5: 棋譜再生・盤面サイズ・CPU改良

- **棋譜再生**：対局中または終局後に「棋譜を再生」から最初・前へ・次へ・最後・スライダーで局面を確認できます。再生中は着手・パス・Undoを無効にし、対局本体を変更しません。「対局へ戻る」で再開します。CPU対戦中は再生中だけCPUの着手も一時停止します。
- **盤面サイズ**：小19マス（半径2）、中37マス（半径3）、標準61マス（半径4）、大91マス（半径5）から選択できます。対局中のサイズ変更は確認のうえ新規対局になります。
- **CPU（むずかしい）**：従来の一手評価に加え、自分の石が呼吸点1になって次のCPUに取られる可能性を限定的にチェックする「guarded」方式に改善しました。網羅的な探索や勝利を保証するものではありません。
- **互換性**：従来のブラウザ自動保存とJSON棋譜はそのまま読み込めます。前のv0.4 APIは維持し、新たに `openReplay()` / `seekReplay(n)` / `closeReplay()` / `getReplayState()` を追加しました。表示用の盤面と実対局の状態を分離しています。

```js
const go = window.threeColorGo;
go.reset({mode:'local',radius:3});
go.play(0,0);
go.openReplay();
go.seekReplay(0);       // 初期盤面の状態を表示
go.getReplayState();    // 表示中の局面をJSONで取得
go.closeReplay();       // 対局へ戻る（石数・履歴は不変）
```

## v0.4: 遊びやすい盤面表示とCPU難易度

- **直前の着手**：盤上に残る直近の着手位置を金色の輪で表示。石が取られた場合は誤解を避けるため表示しません。
- **合法手ガイド**：切り替え式。合法な空点に小さな点が付きます（初期状態OFF）。
- **危険な石**：呼吸点が1つの同色グループに赤い輪を表示（初期状態ON）。危険表示は「次の手で必ず取られる」意味ではありません。
- **CPUの強さ**：やさしい（合法手から乱択）、ふつう（旧baseline）、むずかしい（1手先の捕獲危険も検討するguarded）。この順序は棋力の保証ではなく簡易的なレベル分けです。
- 難易度やガイド表示は対局中に変更可能で、ブラウザ保存・棋譜に含まれます。旧版の保存データも読み込めます。
- 盤面の表示はルール・得点・合法手に影響しません。

## v0.3: 戦略CPU・定量的な自己対局レポート

- CPUは**取れる石**だけでなく、呼吸点が1つの自石の救出、自石の危険、相手の呼吸点を評価する1手読みの戦略AIに変更しました。強い囲碁AIと同等ではありません。
- v0.2 の旧AIは `baseline` として残し、同じ種（seed）で再現可能な比較に使えます。
- CLIでの対局・ブラウザ操作APIは引き続き動作します。ゲームの得点や捕獲ルールは変更していません。
- 対局の勝敗、引き分け、途中打ち切り、手数、占有率、捕獲石数、複数色による共同捕獲を計測します。
- 勝率は同点時に各勝者へ均等配分します。**途中打ち切り局は勝率に含めません**。全員同じAIでの勝率には先手とAI戦術の偏りが含まれます。

```sh
npm test
# 三人とも新AI、300局。棋譜3局分と集計をJSONとして保存
npm run analyze -- --games 300 --seed 2026 --radius 3 --samples 3 --out reports/tactical-300.json
# 旧AI2体 vs 新AI1体。新AIを黒・白・赤に交代させ、各30周（90局）
npm run analyze:compare -- --games 30 --seed 2026 --radius 3 --out reports/rotated-90.json
```

レポートの `sampleRecords[].actions` は既存の棋譜インポート機能で再現できます。
`--games` は通常の分析では実対局数、`--compare` では**各席の実施回数**（実対局は3倍）です。
これはルールの優劣を証明するものではなく、現在の限定的なAI同士の実験です。

## ルール

| 項目 | 内容 |
| --- | --- |
| 人数 | 3人（黒→白→赤） |
| 盤面 | 正六角形。六角マスの中心に石を置く、**6方向接続**の格子 |
| 盤面サイズ | 通常は半径4／61マス。APIでは半径2〜12 |
| 石の連結 | 同色の石が6方向に隣接すると連結 |
| 捕獲 | 集団の空の隣接マス（呼吸点）がゼロになると取り除く。複数色による共同包囲も可 |
| 自殺手 | 禁止（相手を取り、呼吸点を作れる場合は合法） |
| コウ | **全局同形禁止**。パスは例外 |
| 終局 | 3人が連続でパス |
| 得点 | **盤上に残る石1個＝1点**。陣地・アゲハマ・コミは加点しない |
| 勝敗 | 石数最多の色が勝利。同点なら同点者全員が勝者 |

注意：盤上の「死に石」を終了後に自動判定する機能はありません。取る必要のある石は終局前に捕獲してください。

CPUはゲームを極端に長引かせないため、盤面のマス数の2倍の手数を過ぎるとパスする簡易方針です。**強制終局ではなくCPUの行動方針**です。

## 🤖 ChatGPT / Codex / その他AI向け：対局・動作確認

外部エージェントが状態を読み、合法手を選び、実際に打ち、テストできます。詳細は [AGENTS.md](AGENTS.md)。

### 1. ブラウザの操作API

公開サイトまたはローカルサイトを開き、ブラウザのJavaScript実行環境で：

```js
const go = window.threeColorGo;
go.reset({mode:'local',radius:3});
go.getState();            // JSON形式の盤面・手番・得点
go.legalMoves();          // [{q,r}, ...] 合法手一覧
go.play(0,0);             // 黒が(0,0)へ着手
go.pass();                // 現在の色がパス
go.undo();                // 1手戻す
go.exportRecord();        // 棋譜
go.importRecord(record);  // 棋譜を検証して復元
go.autoPlay(100,42);      // 簡易AIが最大100手進める。乱数シード42
```

盤のマスは `g.cell[data-q="0"][data-r="0"]` のような属性で自動操作できます。`getState()` はJSON化できるオブジェクトを返し、UIから独立して結果を確認できます。

### 2. Node.jsで1手ずつAIが対局（外部依存なし）

```sh
printf '%s\n' \
  '{"action":"new","radius":3}' \
  '{"action":"legal"}' \
  '{"action":"play","q":0,"r":0}' \
  '{"action":"state"}' \
  '{"action":"bot"}' \
  '{"action":"export"}' | node scripts/agent-play.mjs
```

入力は**1行1JSON**、出力も**1行1JSON**。利用できる操作は `new`, `state`, `legal`, `play`, `pass`, `undo`, `bot`, `export`, `import`, `simulate`。AIは合法手一覧を確認して任意の手を選べます。自動対局：

```sh
node scripts/agent-play.mjs --selfplay 20 --seed 42 --radius 3
```

20局の対局統計、終了状態、初回の棋譜がJSONで出力されます。
